# 쉐보레 전산 연동 — "POS에서 결제만" 흐름 가능 여부 조사 결과

- 작성: 포스모스 · 2026-08-26
- 결론 요약: **주문 생성 API만으로는 MOU 목표 흐름(전산 담기 → POS에서 결제만)이 성립하지 않는다.**
  토스가 제공하는 세 가지 연동 수단 어디에도 "이미 만들어진 주문을 POS에서 불러와 결제"하는 경로가 없다.

---

## 1. 실증으로 확인된 사실

실제 가맹점(merchantId 129169)에 Open API로 주문을 만들어 POS 화면까지 확인했다.

| 항목 | 결과 |
|---|---|
| 주문 생성 | ✅ 정상 (`orderState: OPENED`) |
| POS [현황] > 진행 탭 표시 | ✅ 실시간 반영 (0분 전) |
| POS가 미결제 인식 | ✅ "결제 전", "남은 금액 3,000원" |
| **POS에서 그 주문 결제** | ❌ **진입점 없음** |

결제 진입점을 찾기 위해 확인한 위치:

| 위치 | 결과 |
|---|---|
| [현황] 카드의 `호출` / `완료` | 결제 아님. 호출=픽업 알림톡, 완료=처리 완료 표시 |
| [현황] 주문 상세 | `주문서 출력`만 존재 |
| 주문 상세 ✏️ 아이콘 | 주문 메모 편집 |
| [주문] 탭 하단 `결제` | 새 장바구니 기준이라 `0원 결제`로 비활성 |
| [주문] 탭 `나중에 결제` | 해당 주문을 불러올 수 없음 |
| `완료` 처리 후 재확인 | 여전히 `남은 금액 3,000원` — **결제 없이 종료됨** |

부수적으로 배제한 가설: `diningOption` 4개 값 전부(`HERE`/`TOGO`/`DELIVERY`/`PICKUP`),
카탈로그 등록 상품(`targetType: ITEM`), `REQUESTED` 상태(`requestedInfo` 포함) — 모두 결과 동일.

## 2. 왜 안 되는가 — 문서상 근거

주문 생성 API는 애초에 **결제를 일으키는 API가 아니다.** 문서 원문:

> "외부 시스템에서 받은 주문 정보를 토스 POS 주문으로 생성하여 **주문 이력을 관리**할 수 있어요"

> "이미 결제가 **모두 완료된** 주문을 생성하는 경우, 주문 생성 API 요청에 결제 내역을 포함하여 전달해야 해요"

> "Open API를 통해 생성한 주문에 포함된 결제건은 모두 **외부결제수단**으로 처리된다는 점에 유의하세요."

즉 `payments` 필드는 **다른 곳에서 이미 결제된 내역을 기록**하는 용도다(배달앱 주문을 POS 매출에
합산하는 것과 같은 성격). 토스 POS로 카드 승인을 일으키는 수단이 아니다.

[현황] 탭에 `호출`/`완료`만 있는 것도 같은 맥락이다 — 이 화면은 원래 주방·픽업 관리용이다.
공식 가이드: **[현황]** = "주문 상태를 모니터링하고 고객을 호출하는 공간",
**[주문]** = "메뉴를 선택하고 옵션을 추가한 뒤 결제하는 공간".

## 3. 세 가지 연동 수단별 결제 가능 여부

| 수단 | 결제 발생 | 기존 주문 지정 | 근거 |
|---|---|---|---|
| **Open API** (서버→토스) | ❌ 기록만 | — | "결제건은 모두 외부결제수단으로 처리" |
| **POS 플러그인 SDK** | ❌ 기록만 | — | **"Toss POS에서만 결제를 생성할 수 있어요"**. `payment.add()`는 "결제가 완료된 후 실행", EXTERNAL 타입 |
| **프론트 플러그인 SDK** | ✅ **실제 승인** | ❌ **불가** | `sdk.payment.requestPayment`는 실제 카드 승인 발생. 단 파라미터가 `paymentKey/tax/supplyValue/tip` 등 **금액뿐** — `orderId`/`orderKey`/`lineItems` 없음 |

**핵심 제약**: 실제 결제를 일으킬 수 있는 건 프론트 플러그인뿐인데, 그건 **금액만 받고 기존 주문을
지정할 수 없다.** 따라서 "미리 만들어둔 주문을 불러와 결제"가 구조적으로 성립하지 않는다.

## 4. 대안 설계

### 안 A — 프론트 플러그인에서 금액 결제 + Open API로 주문 기록 (권장)

```
전산 "담기" → 우리 서버가 주문 내용 보관 (이미 구현됨: ErpOrder 테이블)
   ↓
매장 직원이 프론트 단말기에서 해당 건 선택
   ↓
sdk.payment.requestPayment(금액)  → 실제 카드 결제 발생
   ↓
결제 성공 → 우리 서버가 Open API로 주문 생성 (payments 채워 COMPLETED)
   ↓
POS 매출/주문 이력에 정상 반영
```

- **장점**: 실제 카드 결제가 매장 단말기에서 일어나고, POS 매출 집계에도 잡힌다. 세 수단의 제약을
  모두 우회하는 유일한 조합.
- **필요 작업**: 프론트 플러그인에 "전산 주문 목록 → 선택 → 결제" 화면 추가.
  우리 서버에 주문 조회 API(전산 주문 목록)와 결제완료 후 Open API 호출 로직 추가.
- **유의**: 결제가 "외부결제수단"으로 기록되는지 여부는 실호출로 확인 필요.

### 안 B — 결제를 전산/외부에서 처리하고 POS엔 기록만

전산이나 별도 PG로 결제 → Open API로 COMPLETED 주문 생성.
- **장점**: 구현이 가장 단순 (이미 만든 중개 API에 payments만 추가)
- **단점**: 매장 카드단말기를 안 쓰게 되어 MOU 취지("POS에서 결제만")와 어긋남

### 안 C — 토스에 공식 확인 (선행 권장)

우리가 놓친 경로가 있는지 확인. 특히 지난 회신에서 토스가 명시적으로
**"매장에서 해당 주문을 선택해 결제할 수 있어요"** 라고 답변했으므로, 그 방법을 요구할 근거가 있다.

## 5. 현재 구현 상태

ERP 중개 서버는 이미 구현·배포 완료되어 있고, 위 어느 안으로 가더라도 재사용된다.

- `POST /api/erp/draft-orders` — 전산 주문 수신 → 토스 주문 생성 (멱등)
- `GET /api/erp/draft-orders/:referenceId` — 조회
- `POST /api/admin/stores/:id/erp-code` — 매장코드 매핑
- `ErpOrder` 테이블 — 전산 참조번호 ↔ 토스 주문 매핑 보관
- 테스트 54개 통과

안 A로 갈 경우 추가로 필요한 것은 프론트 플러그인 화면과, 결제 성공 후 COMPLETED 주문을
생성하는 경로뿐이다.
