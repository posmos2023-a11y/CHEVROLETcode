# 전산 주문 → 프론트 직접 결제 (payTarget: front)

## 왜 필요한가

토스는 **프론트 플러그인과 토스 POS 동시 연결을 지원하지 않는다**
([연동 가이드 FAQ](https://docs.tossplace.com/guide/front-integration/faq.html)).
플러그인 모드 프론트는 POS와 페어링되지 않으므로 POS 플러그인이 프론트로 결제를 보낼 수 없다.

그래서 전산 주문을 POS를 거치지 않고 프론트 플러그인이 서버에서 바로 받아 결제하는 경로를 추가했다.
기존 POS 결제 경로(`payTarget` 미지정 = `pos`)는 그대로다.

## 프론트로 보내는 두 가지 방법

| 방법 | 누가 정하나 | 쓰는 곳 |
|---|---|---|
| A. 전산에서 바로 | 전산 앱 "프론트에서 결제" 체크 → `payTarget:'front'` | 처음부터 프론트에서 결제할 걸 알 때 |
| B. 정비 대기열(POS 탭앱)에서 넘기기 | 탭앱 [전산 주문] 카드의 **[프론트 결제]** (3초 안에 두 번) | 손님이 프론트 앞에 왔을 때 직원이 넘김 |

B로 넘긴 주문은 탭앱 **"프론트 결제 대기"** 칸에 보이며, 손님이 결제를 시작하기 전이면
**[POS로 되돌리기]** 로 되돌릴 수 있다. 결제 중이면 되돌릴 수 없다.
프론트로 넘긴 주문은 POS가 담을 수 없다(서버가 409로 막고, 탭앱은 방금 담은 품목을 되돌린다).

전산 앱은 POS로 보낸 건이 프론트로 넘어가면 그걸 감지해 결제 완료까지 최대 5분 기다린다.

## 흐름

```
(B) POS 탭앱 --POST /api/pos/erp-carts/:id/send-to-front--> payTarget pos → front
    POS 탭앱 --POST /api/pos/erp-carts/:id/return-to-pos--> payTarget front → pos (pending일 때만)
전산(ERP) --POST /api/erp/carts {payTarget:'front'}--> 서버(ErpCart: pending)
프론트 대기화면 --GET /api/front/erp-carts (3초마다)--> 주문 발견 → erp-pay.html
손님이 [결제하기] --POST /api/front/erp-carts/:id/start--> paying (+paymentKey)
프론트 SDK requestPayment (카드/간편결제/현금)
  ├ 승인 → POST .../result {result:'paid'}       → paid (예약 연결 시 정비완료 자동)
  └ 취소/실패 → POST .../result {result:'cancelled'|'failed'} → pending (다시 결제 가능)
전산 --GET /api/erp/carts/:ref--> pending → paying → paid
```

- 결제 도중 프론트가 재시작되면, 다음에 대기화면이 켜질 때 `sdk.payment.getPayment`로 승인 여부를
  확인해 보고를 마저 보낸다. 서버는 `paying` 건을 시간으로 자동 되돌리지 않는다(이중결제 방지).
- `paying` 중인 주문은 전산이 취소할 수 없다(409).
- 토스 POS에는 이 주문과 결제가 남지 않는다. 결제는 프론트 결제로만 기록된다.

## 설정

1. 프론트를 **플러그인 모드**로 사용한다(토스 POS와 페어링하지 않음).
2. 프론트 설정 → 플러그인 선택 → **플러그인 설정** → 매장 토큰 입력(또는 QR).
   값은 관리자 웹 [매장 개통 설정] → 해당 매장 → POS 토큰 [보기]와 같다.
3. 전산 앱에서 **"프론트에서 결제 (POS 거치지 않음)"** 를 체크하고 [프론트로 전송].

## 배포

| 대상 | 방법 |
|---|---|
| 서버 | 이 폴더의 `backend`를 배포. 마이그레이션 `20261021120000_erp_cart_front_pay`는 컬럼 추가만 하며 기존 로우는 `payTarget='pos'`로 채워진다. |
| 프론트 플러그인 | `cd front-plugin && $env:CHEVROLET_API_BASE_URL='https://...'; npm run zip` → 개발자센터(토스프론트)에 업로드 |
| 전산 앱 | `erp-simulator`를 exe로 다시 빌드 |
| POS 탭앱 | `cd pos-plugin && $env:CHEVROLET_API_BASE_URL='https://...'; npm run zip` → `-foldered.zip`을 개발자센터(토스 POS)에 업로드 |

## 토스 결제내역 매핑

토스 Open API에는 결제 **목록** 조회가 없다(단건·주문별 조회만). 그래서 결제 웹훅
(`payment.payment.approved.v1` / `cancelled.v1`)이 올 때마다 `TossPayment`에 남기고 전산 주문과 잇는다.

| 결제 경로 | 잇는 기준 |
|---|---|
| POS 결제 | 탭앱이 결제 완료 때 보고한 토스 결제 ID = 웹훅 `payment.id` |
| 프론트 결제 | 같은 매장 + 승인번호 + 금액, 후보가 정확히 1건일 때만 |

- 웹훅이 먼저 오든 결제 보고가 먼저 오든 양쪽에서 잇는다.
- 이어지면 `tossVerifiedAt`이 찍히고, 관리자 웹·탭앱에 "토스 확인"이 표시된다. 결제완료인데 계속
  미확인이면 웹훅 누락이거나 위조된 결제 보고일 수 있으니 확인한다.
- 토스 취소 웹훅이 오면 이어진 주문은 `refunded`로 확정된다(어디서 취소했든).
- 전산 주문과 이어진 결제는 기존 `Payment` 백업 기록을 만들지 않는다.
- ⚠️ 웹훅은 토스 개발자센터 Open API 앱(`posmos-chevrolet-order`)의 웹훅 설정과, 매장에 그 앱이
  설치돼 있어야 온다.

## 결제 취소 (정비 대기열 [전산 주문] → "오늘 결제")

| 결제 | 버튼 | 동작 |
|---|---|---|
| POS 결제 | [결제 취소] | 탭앱이 `posPluginSdk.payment.cancel` 시도. 같은 POS 결제로 묶인 주문은 함께 취소. 실패하면 POS [주문]에서 직접 취소 후 [POS에서 취소했어요]로 기록 |
| 프론트 결제(카드·간편결제·현금영수증 현금) | [프론트에서 취소] | 프론트가 가져가 `requestPaymentCancel`(NICE 카드는 무카드 취소). 손님 카드 필요. 시작 전이면 [취소 요청 철회] 가능 |
| 프론트 현금(영수증 없음) | [현금 환불 처리] | 토스에 취소할 대상이 없어 현금을 돌려주고 기록만 |

상태: `paid` → `refund_requested` → `refunding` → `refunded` (실패·중단 시 `refund_requested`로).

## 남은 일

- POS SDK `payment.cancel`이 카드·현금 결제를 탭앱에서 바로 취소하는지는 실단말기 확인이 필요하다
  (문서상 "Toss POS를 통해 처리"). 안 되면 [POS에서 취소했어요] 경로로 운영한다.
- 프론트 결제의 웹훅 `approvedNo`가 프론트 SDK의 `approvalNumber`와 같은지 실결제로 확인이 필요하다.
- 토스 결제내역에 품목을 남기려면 Open API "주문 생성 + 승인된 결제 기록"(승인 필요 API)을 검토한다.
- 토스 쪽 매출 집계에 프론트 결제가 어떻게 잡히는지는 토스 확인이 필요하다.
