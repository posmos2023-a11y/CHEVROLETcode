# 배포 롤백 절차

> 작성일: 2026-08-27
> 대상: `chevrolet-api` (Cloud Run, `asia-northeast3`, 프로젝트 `tossplugincar-dev`) +
> Cloud SQL `chevrolet-postgres`(DB `chevrolet`, 앱 사용자 `chevrolet_app`)
>
> **배경**: 지금까지 `backend/prisma/migrations/`에 쌓인 마이그레이션 9개는 전부
> forward-only이고 down 스크립트가 없다(Prisma 자체가 자동 다운마이그레이션을 지원하지
> 않는다). 컨테이너는 부팅 시 `docker-entrypoint.sh`가 `prisma migrate deploy`를 실행한다
> (`RUN_MIGRATIONS_ON_BOOT=true`가 기본값, `Dockerfile`/`backend/.env.example` 참고).
> 이 문서가 없으면, 컬럼을 지우는 마이그레이션이 배포된 뒤 문제가 생겼을 때 그 자리에서
> 되돌리는 마이그레이션을 처음부터 작성해야 한다 — 400개 매장이 쓰는 운영 DB 위에서.
>
> **이 환경에는 `gcloud` CLI가 설치돼 있지 않다.** 아래 명령은 실행해서 검증한 것이 아니라
> 공식 문법에 맞춰 서비스명·리전·프로젝트를 이 저장소의 실제 값으로 채운 것이다. 처음
> 실제로 쓸 때는 `--project`/서비스명이 현재 gcloud 기본 설정과 일치하는지 먼저
> `gcloud config list`로 확인할 것.

## 0. 가장 먼저 판단할 것 — 코드만 되돌리면 되는가?

배포에 문제가 생겼을 때 취할 수 있는 롤백은 두 종류다.

| 상황 | 필요한 조치 |
| --- | --- |
| 이번 배포가 **마이그레이션 없이 코드만** 바꿨다 | Cloud Run 리비전만 되돌리면 끝(§1) |
| 이번 배포에 **마이그레이션이 포함**됐지만 **추가만** 했다(테이블/컬럼 추가, nullable 컬럼 추가) | Cloud Run 리비전만 되돌려도 안전한 경우가 대부분(§0.1) |
| 이번 배포의 마이그레이션이 **파괴적**이다(컬럼/테이블 삭제, 컬럼·테이블 이름 변경, 기존 컬럼에 `NOT NULL` 추가) | 리비전만 되돌리면 **깨진다**(§0.2) — 되돌리는 마이그레이션이 필요할 수 있다(§3) |

판단 기준은 오직 하나: **이번에 배포된 마이그레이션이 파괴적인가.** 파괴적 마이그레이션의
정의는 아래 셋 중 하나라도 해당하면이다.

- `DROP COLUMN` / `DROP TABLE`
- 컬럼명·테이블명 변경(`RENAME`) — Prisma가 내부적으로 `ALTER ... RENAME`을 쓰든 `DROP` +
  `CREATE`로 나오든, 옛 이름을 참조하는 코드가 즉시 깨진다는 점에서 동일하게 취급한다
- 기존에 값이 들어있던 컬럼에 새로 `NOT NULL`을 붙임(백필 없이) — 옛 코드가 그 컬럼 없이
  INSERT를 시도하면 그 순간부터 전부 실패한다

반대로 아래는 **비파괴적**이다(코드만 되돌려도 안전).

- 새 테이블 추가
- nullable 컬럼 추가(`ALTER TABLE ... ADD COLUMN "x" TEXT;`처럼 기본값 없이 nullable로 추가)
- 인덱스 추가

### 0.1 "추가만 했는데도" 확인해야 하는 것

이 저장소의 마이그레이션 중 `20260824120000_production_hardening`은 `Reservation.serviceDate`를
**nullable로 추가 → 기존 로우 백필 → `SET NOT NULL`**의 3단계로 나눠서 적용했다(주석에 그렇게
명시돼 있다). 이 방식 자체가 이 문서 §2에서 설명하는 expand-contract 패턴이고, 이미 배포되어
안정화된 뒤라면 그 컬럼은 "옛 코드도 모르는 컬럼"이 아니라 "옛 코드가 이미 다루던 컬럼"이므로
리비전 롤백만으로 문제없다. **위험한 건 nullable 추가와 `SET NOT NULL` 승격을 같은 배포
안에서 같이 내보내는 경우**다 — 그 배포 자체를 롤백하면 옛 코드가 그 컬럼을 채우지 못해
`SET NOT NULL` 제약에 걸린다. 즉 판단할 때 볼 것은 "이번에 새로 나가는 배포가 nullable
추가와 NOT NULL 승격을 한 번에 묶었는가"이지, "저장소에 그런 컬럼이 있는가"가 아니다.

## 1. 코드만 되돌리면 되는 경우 — Cloud Run 리비전 롤백

Cloud Run은 리비전 단위로 트래픽을 라우팅하므로, 새 이미지를 다시 빌드하지 않고 직전
리비전으로 트래픽을 되돌릴 수 있다.

```bash
# 1) 최근 리비전 목록과 트래픽 비율 확인
gcloud run revisions list \
  --service=chevrolet-api \
  --region=asia-northeast3 \
  --project=tossplugincar-dev

# 2) 문제가 생기기 전 리비전(예: chevrolet-api-00042-abc)으로 트래픽 100% 되돌리기
gcloud run services update-traffic chevrolet-api \
  --region=asia-northeast3 \
  --project=tossplugincar-dev \
  --to-revisions=chevrolet-api-00042-abc=100
```

- 되돌린 뒤에도 **문제가 있던 리비전은 삭제하지 말 것** — 원인 분석에 필요하고,
  `update-traffic`은 리비전을 지우지 않으므로 다시 최신으로 되돌리는 것도 같은 명령으로
  가능하다.
- `main`에 push하면 Cloud Build가 자동으로 새 리비전을 만들어 배포한다(트리거가 Dockerfile을
  자동감지, `cloudbuild.yaml` 없음, §운영-참고.txt). 즉 **다음 정상 배포가 나가기 전까지는
  롤백 상태가 유지되지 않는다** — `main`에 아무 커밋도 없이 그대로 두면 되돌린 리비전이
  트래픽을 계속 받지만, 급하게 다른 수정을 올려 재배포하면 그 배포가 다시 최신 리비전으로
  트래픽을 가져간다. 따라서 롤백 후 원인 조치가 끝날 때까지는 `main`에 다른 배포를 올리지
  않도록 팀에 공유할 것.

## 2. 파괴적 변경을 안전하게 배포하는 방법 — expand-contract

**이 문서의 핵심이다.** 컬럼/테이블을 지우거나 이름을 바꿔야 할 때, 그 변경을 한 번의
배포에 몰아넣지 않고 아래 순서로 나누면 롤백은 항상 "Cloud Run 리비전만 되돌리면 되는
문제"로 남는다.

1. **① 코드에서 사용 중단** — 지울 컬럼을 코드에서 더 이상 읽지도 쓰지도 않게 바꾼다.
   컬럼 자체는 스키마에 그대로 둔다(마이그레이션 없음, 코드 변경만). 이 배포는 마이그레이션이
   없으므로 문제가 생겨도 §1의 리비전 롤백만으로 완전히 안전하다.
2. **② 배포·안정화** — ①을 배포하고, 그 컬럼을 정말 아무도 안 쓰는지 로그·트래픽으로 며칠
   지켜본다. 이 기간 동안 문제가 생기면 그냥 리비전을 되돌리면 된다(컬럼이 아직 스키마에
   있으므로 옛 코드도 새 코드도 둘 다 정상 동작한다).
3. **③ 다음 배포에서 삭제** — ①이 안정적으로 돈 걸 확인한 뒤, 별도의 다음 배포에서
   `DROP COLUMN`/`DROP TABLE` 마이그레이션을 낸다. 이 시점에는 이미 어떤 코드(신·구 리비전
   전부)도 그 컬럼을 참조하지 않으므로, 혹시 이 배포 자체를 롤백하더라도(§0 판단 기준상
   이 배포는 파괴적이지만) 되돌아가는 대상 리비전이 ①·② 단계의 "컬럼을 안 쓰는 코드"이지
   "컬럼이 있어야 동작하는 옛 코드"가 아니어서 안전하다.

이름 변경(rename)이 필요할 때도 같은 원리다 — 옛 컬럼명을 바로 지우지 말고, 새 컬럼을
추가 → 코드가 새 컬럼을 쓰도록 전환 → 안정화 → 옛 컬럼 삭제 순서로 나눈다.

이 저장소의 `20260824120000_production_hardening` 마이그레이션 주석이 이미 같은 원리를
컬럼 **추가** 방향으로 쓰고 있다("nullable로 추가 → 백필 → SET NOT NULL 3단계로 나눈다") —
컬럼을 지우거나 이름을 바꿀 때도 똑같이 단계를 나누라는 것이 이 섹션의 요지다.

## 3. 되돌리는 마이그레이션을 써야 할 때

expand-contract를 못 지키고 파괴적 마이그레이션이 이미 나가버렸다면(예: `DROP COLUMN`이
배포됐고 그 컬럼이 있어야 하는 옛 코드로 리비전을 되돌려야 하는 상황), 코드만 되돌려서는
해결되지 않는다.

- **Prisma는 자동 다운마이그레이션이 없다.** "되돌리는 마이그레이션"은 결국 스키마를 원래
  모습으로 만드는 **새로운 forward 마이그레이션**을 하나 더 작성해서 배포하는 것이다(예:
  지워진 컬럼을 다시 `ADD COLUMN`으로 추가). 기존 마이그레이션 파일을 고치거나 지우면 안
  된다 — `backend/prisma/migrations/`의 각 폴더는 이미 배포된 이력이고, 파일을 사후에
  바꾸면 `prisma migrate deploy`가 체크섬 불일치로 실패한다.
- **`_prisma_migrations` 테이블을 손으로 건드리지 말 것.** 행을 지우거나 `finished_at`/
  `rolled_back_at`을 직접 UPDATE하면 Prisma가 다음 `migrate deploy`에서 실제 스키마 상태와
  이력이 어긋난 걸로 착각해 엉뚱한 마이그레이션을 재적용하거나 거부할 수 있다. 이력을 맞추는
  유일하게 안전한 방법은 새 마이그레이션을 추가하는 것뿐이다.
- **컬럼을 다시 만든다고 데이터가 돌아오지 않는다.** `DROP COLUMN`으로 지워진 값은 스키마를
  복구해도 비어 있다 — 이 경우 데이터 자체를 되살리려면 §4의 백업/PITR 복원이 필요하다.
  스키마만 급히 맞추고(옛 코드가 다시 동작하게) 데이터는 백업에서 나중에 채워 넣는
  전략도 가능하다는 걸 감안하고 판단할 것.
- 작성 절차: 로컬 devdb에서 `npx prisma migrate dev --create-only`로 초안을 만들고, 생성된
  SQL을 검토·수정한 뒤(예: `ADD COLUMN`에 예전과 같은 타입·제약을 그대로 맞춘다) 커밋한다.
  이후 정상적인 배포 경로(§운영-참고.txt "배포": `main` push → Cloud Build → 컨테이너 부팅
  시 `prisma migrate deploy`)로 나간다. **급하게 리비전을 살려야 해서 정식 배포를 기다릴
  여유가 없다면** Cloud SQL Auth Proxy 등으로 운영 DB에 직접 연결해 그 마이그레이션 폴더만
  `npx prisma migrate deploy`로 먼저 적용한 뒤, 뒤이어 코드 배포를 정상적으로 진행하는
  방법도 있다 — 이 경우도 마이그레이션 폴더/파일은 반드시 커밋해서 이력에 남겨야 한다(운영
  DB에만 적용하고 커밋을 빠뜨리면 다음 배포 때 다른 환경과 스키마가 어긋난다).

## 4. 되돌리기 전에 확인할 것 (체크리스트)

- [ ] **백업/PITR 시점 확인이 먼저다.** 지워진 데이터를 되살려야 하는 상황이라면 Cloud SQL의
      백업 또는 PITR(point-in-time recovery)로 파괴적 변경 **직전** 시점을 복원할 수 있는지
      먼저 확인한다.
      **확인 필요 — 이 저장소에서 확정할 수 없는 사실**: `chevrolet-postgres` Cloud SQL
      인스턴스의 실제 자동 백업 활성화 여부, 보관 기간, PITR 사용 가능 여부는 코드/문서
      어디에도 기록되어 있지 않다. `docs/gcp-migration-and-scale-plan.md`의 작업 목록에
      "Cloud SQL 백업·자동 유지보수·접속 정책 설정"이 아직 미완료(`[ ]`)로 남아 있어, 실제로
      설정됐는지 자체가 불확실하다 — 콘솔(`Cloud SQL → chevrolet-postgres → 백업`)에서 직접
      확인할 것.
- [ ] 문제가 된 배포가 정확히 어떤 마이그레이션을 포함했는지 `git log`로 확인
      (`backend/prisma/migrations/`에서 그 배포 커밋에 새로 추가된 폴더).
- [ ] 그 마이그레이션이 §0의 파괴적 변경 기준에 해당하는지 다시 확인.
- [ ] 되돌릴 Cloud Run 리비전이 "그 마이그레이션 이전 스키마"를 전제로 짠 코드가 맞는지 확인
      (리비전 목록의 배포 시각과 마이그레이션 커밋 시각을 대조).
- [ ] 트래픽이 적은 시간대인지 확인(가능하면 새벽 등 영향 최소 시간대에 진행).
- [ ] 롤백/복구 작업을 시작한다고 관련자에게 공유(특히 여러 매장에 영향을 줄 수 있는 변경).

## 5. 배포(또는 롤백) 직후 확인할 것

```bash
curl https://chevrolet-api-813801981857.asia-northeast3.run.app/health
# -> "ok" (liveness, DB 접근 없음)

curl https://chevrolet-api-813801981857.asia-northeast3.run.app/health/ready
# -> {"ok":true} (readiness, SELECT 1로 DB 연결까지 확인)
```

- `/health/ready`가 `503 {"ok":false}`를 반환하면 DB 연결 또는 스키마 문제이니 바로
  Cloud Logging을 본다.
- Cloud Logging(`https://console.cloud.google.com/logs/query?project=tossplugincar-dev`)에서
  부팅 로그를 확인한다 — 특히 `docker-entrypoint.sh`가 남기는 아래 문구를 찾는다.
  - `migrate deploy failed - running migrate status ...` — 락 경합으로 실패했다가 다른
    인스턴스가 스키마를 최신으로 만들어 정상 기동했다는 신호. 그 자체는 정상 상황이지만
    반복해서 나타나면 인스턴스 동시 콜드스타트가 잦다는 뜻이니 `RUN_MIGRATIONS_ON_BOOT`
    분리(§`TODO.md`)를 검토한다.
  - `schema is still not up to date after retries - migration genuinely failed, exiting` —
    마이그레이션이 진짜로 깨졌다는 뜻. 이 경우 그 리비전은 계속 크래시 루프에 빠지므로
    §1의 트래픽 롤백을 즉시 수행한다.
- 애플리케이션 로그에서 새로 늘어난 에러(500, 특히 컬럼 없음/제약 위반 관련 Postgres 에러)가
  있는지 확인한다.
